## Item 1 — per-edge `sin`/`cos` tables (P1's headline)

| | before | after | |
|---|---:|---:|---|
| eager plan build | **12.918 s** | **4.698 s** | **2.75×** |
| `_rastercellcap`, one cell | 216.3 ns | 45.2 ns | **4.79×** |
| cold lazy chunk, **A** bands 1/2/3 | 4.564 / 1.960 / 4.220 s | 2.602 / 0.765 / 1.685 s | 1.8–2.7× |
| cold lazy chunk, **B** bands 3–6 | 0.578 / 0.550 / 0.541 / 0.540 s | 0.219 / 0.217 / 0.211 / 0.210 s | 2.6× |

P1 estimated 54 % off the build from a 5.08× prototype; measured 63.6 % off from
a 4.79× one.

**What changed.** A `chartedgetables(transform, xedges, yedges)` hook, `nothing`
by default, returning `LonLatEdgeTables` for `LonLatToSphere` — `cosd`/`sind` of
both edge vectors plus the widest longitude step, `O(nx + ny)`. `RasterGrid` gains
a `tables` field (and a fifth type parameter). `_cellcorners` reads a corner as
`(cy[j]·cx[i], cy[j]·sx[i], sy[j])`; `_rastercellcap` builds the cap from those
four corners in `_cornercap`, which is `_boxcap`'s arithmetic with the same sums
in the same order; `getcell` goes through the same corners. A chart with no table
method keeps the per-point path unchanged.

**Bit-identity evidence.** `test_rastergrid.jl` "edge tables" keeps `@noinline`
transcriptions of the pre-change `_boxpoint`/`_boxcap`/ring constructions and
asserts equality **of bits** (`===` per component, so a `-0.0` would fail) for the
cell cap and the `getcell` ring of *every* cell of five rasters — forward,
reversed latitude, transposed, 0–360, and a 72×36 fine one, 8 148 cells — plus the
plan digest above. An `OpaqueChart` raster asserts `tables === nothing` still
answers, and answers what the tabulated raster answers.

## Item 2 — the whole-sphere cap bailout (P1's L2 failure)

Chunking **B**, destination band extents:

| | radii (rad) | discovered pairs | truth |
|---|---|---:|---:|
| before | `[0.394, 0.879, 1.408, π, π, π, π, 1.408, 0.879, 0.394]` | **116** | 48 |
| after | `[0.314, 0.628, 0.943, 1.257, 1.571, 1.571, 1.257, 0.943, 0.628, 0.314]` | **96** | 48 |

Over-report 2.42× → 2.00×; bands 4–7 build **16 → 12** blocks each. Chunking **A**:
the equatorial 360° band goes π → 2.0948, which is the smallest a cap containing
the whole equator can be — a band straddling the equator legitimately stays large.
A 36×18 raster cut into six pole-to-pole **stripes** goes π → 1.5710, and stripe 1
no longer contains the meridian opposite it.

Eager cost: **+1.0 %** (interleaved medians, 4.496 s off / 4.543 s on).

**What changed.** `_bowedband` bounds the latitude band a box's cells occupy —
an east–west cell edge is a great-circle arc that bows to `atan(tan φ / cos(Δλ/2))`
poleward of its parallel, and the meridians bounding a box do not bow. `_polarcap`
turns that band into a cap about a pole (`{lat ≥ a}` **is** a cap of radius
`90° − a`), which needs no convexity and holds for a box of any longitude span;
`_widecap` also offers a cap on the box's mid-meridian when the box is under 180°
wide, whose farthest point is a corner. `_rectcap` takes the tighter of the
sampled cap and `_widecap`.

**Coverage evidence.** The tests densify every cell ring's great-circle edges
(7 points per edge) and assert containment in the chunk cap *and* in every node
extent of the cell tree, for the banded raster, the stripe raster, and an
equator-straddling band. Plus the discriminating half: a southern band's cap does
not contain the north pole, and no band's cap has radius π. Corner containment
alone would not have caught an under-covering bound, since the cells bow outside
their graticule boxes.

`test/toyspaces.jl` had the same bail. Change is additive: a documented
`toy_bandcap(lat0, lat1, dlon)`, used by `chunktree` **only where `toy_cap`
degenerates to the full sphere**, so every cap the toy produced before is the cap
it produces now. `test_conservative.jl` asserts the same covering law and the
same "does not reach the far pole" for a globally banded toy space.

**Where the cost of this went** — worth recording, because the first version was a
19 % regression. Calling the fallback from inside `_boxcap`'s two bail branches
cost the eager build **+0.85 s** for **22 actual invocations**: instrumented, the
two configurations run an identical descent (600 726 `_rectcap` and 41 452 704
cell-cap evaluations either way), so the whole cost was what the call did to the
codegen of the 600 726 nodes that never take the branch. `_boxcap` is back to
returning `_WHOLE_SPHERE`, and the fallback lives in `_rectcap` behind a
two-subtraction gate: a cap that survived and is already tighter than `90° − |φ|`
cannot be beaten by either wide construction.

## Item 3 — `_cellring` push!-growth

| | before | after | |
|---|---:|---:|---|
| eager plan build | 4.698 s | **4.427 s** | 1.06× |
| allocated | **4.48 GiB** | **3.33 GiB** | **−26 %** |

**What changed.** `_ringlength` counts the distinct corners first — consecutive
repeats dropped, and a tail equal to the head — so the ring is allocated once at
its final length instead of grown. `getcell` allocates 256 B afterwards.

**Identity evidence.** The "edge tables" testset compares the ring against the
growing construction for every cell of the five rasters *and* for all 81 ways four
corners can repeat, which is where the polar special case lives.

## Item 4 — double sparse assembly

At P1's mid size (nnz 7 120 800), fresh process:

| | `findnz` | direct | |
|---|---:|---:|---|
| `Sys.maxrss` delta | **1735.5 MiB** | **1640.7 MiB** | **−94.8 MiB (−5.5 %)** |
| allocated | 35.84 GB | 35.68 GB | −159 MB = **24 B/nnz**, exactly the triple |
| build | 49.8 s | 44.6 s | within run-to-run noise |
| block hash | `18356831990037488270` | `18356831990037488270` | identical |

At 1/9 scale the same change is −19 MB allocated, which is under the maxrss noise
floor (±20 MiB) — hence the mid-size measurement.

**What changed.** `_fillcoo!(coo, block)` reads CR's assembled `SparseMatrixCSC`
in place, column-major over the stored entries — the order `findnz` produced — so
the weights and the accumulated denominators are the same `Float64`s. A generic
`AbstractMatrix` method keeps it total if CR ever returns something else.

**Identity evidence.** A new testset builds a whole-domain block and asserts
`block.weights == areas` and `block.denom == vec(sum(areas; dims = 2))` against
`CR.intersection_areas` over the same two trees, with no tolerance.

Not done, deliberately: pushing the operator's triplets straight into the
`WeightCOO` and skipping CR's matrix as well. It would remove a second copy, but
the denominators would then accumulate in descent order rather than column-major,
which is a different `Float64` in the last bits — and item 4 was promised
identical.

## Item 5 (P1's P2, per-chunk cap memoization) — deferred to T8

After item 1 the penalty it targets is not there to remove at this scale: a cold
lazy read costs **2.5 µs/nnz** (chunking B, bands 4 and 5) against **5.3 µs/nnz**
for the whole-domain eager build, where P1 measured 75.7 against 18.4. The polar
band is the remaining outlier at **16.3 µs/nnz** (3.1× the eager rate), where the
blocks are sparse and the cells tiny. A cache that survives across block builds
has to sit beside the block in `plans.jl` or on the plan — both T8's — because a
chunk's tree is constructed fresh for every build and can hold nothing.

## Net effect

| | before | after |
|---|---:|---:|
| eager conservative plan build (720 k → 7.2 k cells) | 12.918 s | **4.220 s** (3.06×) |
| allocated by that build | 4.49 GiB | **3.31 GiB** (−26 %) |
| cold lazy chunk read, **B** bands 3–6 | 0.578 / 0.550 / 0.541 / 0.540 s | **0.210 / 0.205 / 0.201 / 0.208 s** (2.6–2.8×) |
| discovered chunk pairs, **B** (truth 48) | 116 | **96** |
| peak resident, mid-size build | 1735.5 MiB | **1640.7 MiB** |

For scale against P1's own baseline: the mid-size whole-domain conservative build
now takes **44.6 s** in a fresh single-threaded process, against the 133.25 s P1
recorded. That is not an A/B — the two were not run in one session — so treat the
per-item numbers above as the measurements and this as the order of magnitude.

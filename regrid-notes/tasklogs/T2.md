# T2 — `RasterGrid`

`src/rastergrid.jl` implements the whole `RegridSpace` contract for a
DimensionalData raster plus both trees. `test/test_rastergrid.jl` is 54 green
assertions. The suite's one remaining failure is **not** T2's: `runtests.jl:83`
asserts `build_weights!(…, Conservative(), …)` throws, which stopped being true
when T3 landed. That line lives in a file T2 does not own.

## FLATTENING CONVENTION — read this first

Cell positions enumerate the two spatial dimensions **in the array's own
dimension order, fastest first**.

| `dims(A)` | position of cell `(ix, iy)` |
|---|---|
| `(X, Y, …)` | `ix + (iy - 1) * nx` — X fastest, same as `ToyLonLatSpace` |
| `(Y, X, …)` | `iy + (ix - 1) * ny` — Y fastest |

So `vec` of a spatial slice of the raster **is** position order, with no
permutation, whichever way round the array is stored. `space.xfast` is the flag;
`cellsubscript(space, i) -> (ix, iy)` and `cellposition(space, ix, iy)` are the
mapping, and nothing downstream should re-derive the arithmetic. `ix` always
indexes the X dimension and `iy` the Y dimension regardless of storage order.

Chunk numbers use the same convention over the chunk lattice:
`chunksubscript(space, c) -> (cx, cy)`, `chunkbox(space, c) -> (xrange, yrange)`.

`rastersize(space)` gives the spatial shape in array order and `DD.dims(space)`
the two dims in array order — that pair is what the executor needs to reshape.

## Constructor

```julia
RasterGrid(A::DD.AbstractDimArray; xdim, ydim, chunks, transform, inverse, xperiod, ybounds)
RasterGrid(dims::Tuple; chunks = nothing, …)      # same kwargs; no array, no chunking
RasterGrid(xd, yd; …)                             # varargs form of the above
```

O(1) in the cell count: `O(nx + ny + nchunks)` work, no polygon materialized, no
element of `A` read (a test asserts zero `readblock!` calls on a disk-backed
parent through construction, both trees, and every `getcell`).

Fields and their semantics:

| field | meaning |
|---|---|
| `xdim`, `ydim` | the two DD dimensions, stored so downstream can rebuild output dims |
| `xedges`, `yedges` | `n+1` cell edges **in lookup order**, strictly monotone — descending for a reverse-ordered lookup |
| `xchunks`, `ychunks` | `Vector{UnitRange{Int}}` per axis, ascending, partitioning `1:nx` / `1:ny` |
| `transform` | callable `(x, y) -> USPoint` |
| `inverse` | callable `p -> (x, y)`, or `nothing` (then `cellat` throws) |
| `xperiod` | period of native X, or `nothing`; `cellat` reduces by it |
| `xfast` | see the table above |
| `ccw` | whether ascending-native corner order is already CCW from outside |

Dimensions are found by `DD.XDim`/`DD.YDim`, then by name (`x`, `lon`, `long`,
`longitude` / `y`, `lat`, `latitude`); `xdim`/`ydim` override. Extra dimensions
(time, band) are ignored, and their chunking is dropped.

Edges: `Intervals` lookups use `DD.intervalbounds` (non-abutting intervals
throw — an edge vector cannot describe a gappy axis); `Points` lookups are
midpointed with the outer two edges extrapolating the first and last
half-widths. Y edges are clamped into the chart's `ybounds`, then both vectors
are checked strictly monotone.

Chunks come from `DiskArrays.eachchunk(parent(A))` when `haschunks` is
`Chunked` and the result is a `GridChunks`; anything else is one whole-domain
chunk. Only the X and Y dimensions' chunk splits are kept.

## The transform seam (projected rasters)

`transform` is any callable `(x, y) -> UnitSphericalPoint`. Three unexported
hooks parametrize the rest:

```julia
chartinverse(t)            # -> callable `p -> (x, y)`, default `nothing`
chartlimits(t)             # -> (xperiod, ybounds), default (nothing, nothing)
LonLatToSphere(), SphereToLonLat()   # the shipped degrees chart
chartinverse(::LonLatToSphere) = SphereToLonLat()
chartlimits(::LonLatToSphere) = (360.0, (-90.0, 90.0))
```

A projected raster passes `transform =` its own callable and either defines
those two hooks for its type or passes `inverse`/`xperiod`/`ybounds` directly.

**Winding adapts to the chart.** `getcell` builds its corners in
ascending-native order `(xlo,ylo), (xhi,ylo), (xhi,yhi), (xlo,yhi)`, which
discards the lookup order entirely; the *chart's* handedness is measured once at
construction (Newell normal of the widest of nine probe cells, dotted with the
outward radial) and stored in `ccw`, and the ring is reversed when that says so.
A chart that flips handedness therefore still yields CCW-from-outside rings, and
so does any combination of reverse-ordered lookups. This is the root of
acceptance law 4 and the "lookup order" testset is what holds it.

Cells are **geodesic quadrilaterals** through their four corners — parallels are
not densified — so neighbouring cells share an edge exactly and a global
raster's polygon areas sum to `4π`. Same stance as `ToyLonLatSpace`; do not
assert polygon area against the graticule area `Δλ (sin φ_hi − sin φ_lo)`.

`cellat` inverts the chart, reduces X by `xperiod`, and binary-searches both
edge vectors (handling descending vectors), so it is `O(log nx + log ny)`.
Shared edge → the cell on the larger-native side; the raster's own outer edge →
inward; outside coverage → `nothing`.

## Tree shapes

**`celltree(space)` — `RasterCellTree`, O(1) to build, O(1) memory.** A binary
recursion over the index rectangle `(ix0:ix1, iy0:iy1)`, halving the longer side
down to 16 cells. It stores *nothing but the rectangle*: node extents are
derived on demand from the rectangle's native box and marked
`node_extent_is_expensive = true` so the dual descent caches them; leaf entries
are `(cell position, four-corner cap)`. That is what makes a raster of any size
treeable — no per-cell array is ever allocated.

Covering law: a node's cap is centred on the mean of `4(nsamp+1)` box-boundary
samples, sized to reach the farthest, and downgraded to the full sphere past
`π/2`. Under a lon–lat chart the box's farthest point from any centre is a
corner, so the cap contains every cell corner in the box; a cap of radius ≤ π/2
is convex, so it also contains the geodesic arcs between them — i.e. the cell
polygons, which bow outside the graticule box. Tested recursively.

Note a parent's cap does **not** contain its children's caps as caps (children
are dilated outward). That is fine — STI prunes on `intersects` and every node's
extent covers the real geometry beneath it — but do not assert cap nesting.

**Chunk-restricted subtrees for T3/T5/T7:**

```julia
celltree(space, chunk::Int)                     # RasterCellTree over the chunk's rectangle — O(1)
celltree(space, indices::AbstractVector{<:Integer})  # RasterFlatTree, one stored cap per cell
```

Leaf indices are **global cell positions** in every case, matching what
`conservative.jl`'s `subtree` docstring requires, so localization to block-local
indices stays in the weight builder.

**`chunktree(space)` — `RasterFlatTree`**, one node, stored caps, leaf indices
are chunk numbers. Modelled on `ToyCapTree`; `O(nchunks)`. A chunk's cap is the
same box cap, so it covers every cell `cellindices` assigns to it (tested).

Both tree types implement `Trees.ncells`, `Trees.getcell(tree, i)`,
`Trees.getcell(tree)` and `GOCore.best_manifold`, so
`ConservativeRegridding.intersection_areas` consumes them directly. Verified
end-to-end in the tests: a coarse `RasterGrid` against a fine one gives exactly
`4π` total, each coarse row its own area, unchanged when the source's latitude
lookup is reversed.

`cellindices(space, chunk)` returns a `UnitRange` exactly when the chunk spans
the whole **fastest** dimension (X for an `(X, Y)` array, Y for a `(Y, X)` one),
and a `Vector{Int}` otherwise; ascending in both cases.

## Seams for later waves

1. **`hascellchart(::RasterGrid) = true` but T4's chart interface is not
   implemented.** T4 declared `chartaxes`, `chartcoords`, `chartposition`,
   `chartperiod` in `interpolation.jl`, which is included *after*
   `rastergrid.jl`, so T2 could not define methods against them without a
   forward reference to a file being written in parallel. T6 should add, in
   whichever file it prefers:

   ```julia
   chartaxes(s::RasterGrid) = ([(s.xedges[k] + s.xedges[k+1]) / 2 for k in 1:_nx(s)],
                               [(s.yedges[k] + s.yedges[k+1]) / 2 for k in 1:_ny(s)])
   chartcoords(s::RasterGrid, p) = s.inverse === nothing ? nothing : s.inverse(p)
   chartposition(s::RasterGrid, ix::Int, iy::Int) = cellposition(s, ix, iy)
   chartperiod(s::RasterGrid) = (s.xperiod, nothing)
   ```

   Until then `BilinearPoint` over a `RasterGrid` is a `MethodError`, not a
   clean message.

2. **`subtree(space, inds)` has no `RasterGrid` method**, for the same
   include-order reason. T3's generic fallback builds one polygon per cell;
   T6 should add `subtree(s::RasterGrid, inds) = celltree(s, inds)` (and
   `subtree(s::RasterGrid, ::Colon)`-style whole-space handling is already
   covered by T3's `_iswholespace`). Better still for a chunk-shaped index set:
   `celltree(space, chunk)` keeps the O(1) rectangle tree.

3. **Duplicate private constant.** `_FULL_SPHERE` is defined in
   `conservative.jl`; T2 uses `_WHOLE_SPHERE` for the identical value to avoid
   redefining it. Worth unifying into one module-level constant.
   `_cellcap` is likewise T3's; T2's analytic version is `_rastercellcap`.

4. **New unexported names in `rastergrid.jl`** (the module file is frozen, so
   none are exported): `LonLatToSphere`, `SphereToLonLat`, `chartinverse`,
   `chartlimits`, `cellsubscript`, `cellposition`, `cellbox`, `chunksubscript`,
   `chunkbox`, `rastersize`, `RasterCellTree`, `RasterFlatTree`.
   `cellsubscript`/`cellposition` deliberately match `ToyLonLatSpace`'s chart
   shape. T9 should consider exporting `RasterGrid`'s chart accessors alongside
   the contract.

5. **`DD.dims(::RasterGrid)` is extended** to return the two spatial dims in
   array order. T5/T9 building a raster destination's output dims should use it
   rather than reaching into the fields.

6. **Extra (non-spatial) dimensions' chunking is discarded.** A raster chunked
   along time contributes nothing to `nchunks`; the executor owns iterating
   non-spatial slices.

**T6 correction (chart trait).** `hascellchart(::RasterGrid)` is now
`space.inverse !== nothing` rather than unconditionally `true`: the chart a
`BilinearPoint` stencil is written against needs the inverse transform to place a
destination centroid on it, so a raster built with `inverse = nothing` gets the
clean "use Conservative() or NearestCell()" message instead of a later failure.
The five chart accessors and `subtree(::RasterGrid, inds)` of seams 1 and 2 are
landed in `rastergrid.jl`; `chartspacing` goes through a new `chartarcs(transform,
dx, dy)` hook, the third of the `chartinverse`/`chartlimits` family.
